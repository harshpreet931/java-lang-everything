<InShort>
the **Java Native Interface** (JNI) is the original way to call C from java: declare a method `native`, generate a C header with **`javac -h`**, implement the function in C against the **`JNIEnv`** API, compile a shared library per platform, and load it with **`System.loadLibrary`**. it's been in java since 1.1 and runs a huge amount of existing code.

since java 24 ([JEP 472](https://openjdk.org/jeps/472)) loading a native library is a **restricted** operation: it prints a warning today, and is planned to need `--enable-native-access` in the future. for new code, the [FFM API](/learn/performance/ffm-api) does the same job without the C glue.
</InShort>

## the picture

with FFM, java learned to speak C. with JNI, you hire a translator who lives in C: a small layer of C functions with very particular names, written by you, compiled by you, for every operating system and CPU you ship to. the translator can talk back to the JVM through a phone book of about 230 functions (`JNIEnv`): "give me this string's characters", "make a new array", "call this java method", "throw this exception".

a few things to notice in there:

- **the names are the contract.** `Java_Greeter_add` is found by name when the method is first called (or registered explicitly with `RegisterNatives`). rename the class or move it to a package and the C function name must change too, which is why you regenerate the header.
- **primitives cross for free, objects don't.** `jint` is just an `int`. a `jstring` is an opaque handle; C has to ask the JVM for a copy of the characters and give it back.
- **the library is per platform.** `libgreeter.dylib` on macOS, `libgreeter.so` on linux, `greeter.dll` on windows, each built separately, often for two CPU architectures each. libraries like sqlite-jdbc or netty's native transports ship a dozen binaries inside the jar and pick one at runtime.

<Quiz question="your C function calls a java method through env->CallVoidMethod, and that java method throws. what happens in the C code?" options={["the C code unwinds immediately, like a java exception", "nothing: the exception is pending and C keeps running", "the JVM crashes", "CallVoidMethod returns -1"]} answer={1}>
<Explain>
nothing visible: C has no exceptions. the JVM marks an exception as *pending* on the thread and `CallVoidMethod` simply returns. your C code keeps running, and if it calls most other JNI functions with an exception pending, the behaviour is undefined. you're supposed to check `(*env)->ExceptionCheck(env)` after every call that can throw, and return (so java sees the exception) or clear it. forgetting is one of the classic JNI bugs, and `-Xcheck:jni` will tell you about it.
</Explain>
</Quiz>

## why it's being fenced in

JNI code runs in the same process as the JVM with no checks at all. a native library can read or write any memory, corrupt the heap, or crash the whole JVM (you get an `hs_err_pid<n>.log` and the process is gone). and until java 24, any library on the class path could do that silently: a dependency of a dependency could load native code without anyone in the application deciding it should.

[JEP 472](https://openjdk.org/jeps/472) (java 24) makes native access an explicit decision, the same way strong encapsulation made deep reflection one ([reflection](/learn/meta/reflection)):

| | jdk 23 and earlier | jdk 24 and 25 | planned (a future release) |
| --- | --- | --- | --- |
| `System.loadLibrary`, declaring `native` methods | allowed, silent | allowed, warning once per module | throws `IllegalCallerException` unless enabled |
| FFM downcalls and upcalls | warning (since 22) | warning once per module | same |
| opt in | n/a | `--enable-native-access=ALL-UNNAMED` (or module names), or `Enable-Native-Access` in the jar manifest | same |

and since java 24 there's a tool to find out who needs it before you flip the switch, `jnativescan`:

```bash
$ jnativescan --class-path greeter.jar
greeter.jar (ALL-UNNAMED):
  Greeter:
    Greeter::add(int,int)int is a native method declaration
    Greeter::greet(String)String is a native method declaration
    Greeter::<clinit>()void references restricted methods:
      java.lang.System::loadLibrary(String)void
```

run it over your application's class path and you get the list of jars that do native things, which is the list of modules to name in `--enable-native-access`.

<Gotcha title="the five classic JNI bugs">
1. **forgetting to release.** `GetStringUTFChars`, `GetIntArrayElements` and friends may copy; every one needs its matching `Release...`, or you leak native memory.
2. **local reference overflow.** every object handle a native method creates is a local reference that lives until the method returns. in a loop over a big array, call `DeleteLocalRef`, or the reference table grows without bound (the spec only guarantees room for 16 without asking for more).
3. **caching a `jclass` or `jobject` across calls.** local references die when the native method returns. keep one with `NewGlobalRef`, and delete it when you're done.
4. **ignoring pending exceptions** (the quiz above).
5. **assuming UTF-8.** `GetStringUTFChars` returns *modified* UTF-8: the character `\0` becomes two bytes, and characters outside the basic plane become two 3-byte surrogates. fine for printing, wrong for anything that expects real UTF-8.

run with `-Xcheck:jni` while developing: the JVM validates every JNI call and complains about most of these.
</Gotcha>

<Deep title="where JNI still makes sense">
for new code, FFM covers almost everything JNI does: calling C functions, passing structs and arrays, callbacks, and with jextract you don't write descriptors by hand. JNI still shows up where you need to work *with* java objects from native code in ways FFM doesn't aim for (calling back into arbitrary java methods with java objects as arguments, from inside a native library), in embedding scenarios (a C program that creates a JVM with the invocation API, `JNI_CreateJavaVM`), and in the long tail of existing libraries that work and that nobody is going to rewrite. the JDK itself still has plenty of JNI inside. and the restriction is about consent, not removal: JNI isn't deprecated.
</Deep>

<Interview q="what is JNI, and why does java 24 warn when you use it?">
JNI lets java call native code: you declare methods `native`, generate a header with `javac -h`, implement them in C against the `JNIEnv` API, build a shared library per platform and load it with `System.loadLibrary`. it's powerful and unsafe: native code runs in the JVM's process with no memory safety, so one bug can corrupt the heap or crash the JVM, and any library could load native code without the application knowing. JEP 472 in java 24 made loading native libraries a restricted operation: it warns today and is planned to require `--enable-native-access` (or a manifest entry) in the future, so using native code becomes a visible decision of the application. `jnativescan` lists which jars need it. for new code, the FFM API does the same job without C glue, and its downcalls measured faster than JNI on my machine.
</Interview>

<Keylines>
- JNI: `native` methods, `javac -h`, C against `JNIEnv`, a shared library per platform, `System.loadLibrary`.
- primitives cross cheaply; objects need JNI calls, and every acquire needs a release.
- a native bug crashes the whole JVM. `-Xcheck:jni` while developing.
- since java 24, native access warns. opt in with `--enable-native-access`; `jnativescan` finds who needs it.
- for new code, use the FFM API: no C glue, and faster calls.
