<InShort>
`Proxy.newProxyInstance` makes an object that implements any **interfaces** you name, at runtime, and sends every call on it to one method you write: **`InvocationHandler.invoke(proxy, method, args)`**. log it, check it, wrap it in a transaction, forward it to a real object, or answer it yourself.

that one trick is how Spring's `@Transactional`, Spring Data repositories, Retrofit and Feign clients work. and it only works for interfaces.
</InShort>

## the picture

you know how you can write `interface UserRepository extends JpaRepository<User, Long>`, never implement it, and still call `repo.findById(7)`? somebody implemented it. at runtime.

think of a receptionist who answers every extension in a building. you dial "billing" or "support" (a method), the receptionist (the handler) picks up every single call, notes who called and why, and then either transfers you to the real person (the target), or just answers the question themselves. the caller can't tell the difference: it dialed the number it wanted, it got an answer.

## a logging proxy

```java title="Main.java" run output="→ greet [ada]\n← hi ada\nhi ada\n→ count null\n← 1\n$Proxy0 implements [interface Main$Greeter]"
import java.lang.reflect.*;
import java.util.Arrays;

interface Greeter {
    String greet(String name);
    int count();
}

class RealGreeter implements Greeter {
    public String greet(String name) { return "hi " + name; }
    public int count() { return 1; }
}

void main() {
    Greeter real = new RealGreeter();
    InvocationHandler logging = (proxy, method, args) -> {
        IO.println("→ " + method.getName() + " " + Arrays.toString(args));
        try {
            Object result = method.invoke(real, args);
            IO.println("← " + result);
            return result;
        } catch (InvocationTargetException e) {
            throw e.getCause();  // rethrow what the real method threw
        }
    };
    Greeter g = (Greeter) Proxy.newProxyInstance(
        Greeter.class.getClassLoader(),
        new Class<?>[] { Greeter.class },
        logging);

    IO.println(g.greet("ada"));
    g.count();
    IO.println(g.getClass().getName() + " implements " + Arrays.toString(g.getClass().getInterfaces()));
}
```

three arguments: a class loader to define the new class in, the interfaces it should implement, and the handler. what comes back is an instance of `$Proxy0`, a class that didn't exist until that line ran. `count()` has no arguments, and notice the handler gets `null` for that, not an empty array.

## what the JVM generated

the proxy class is real bytecode, generated by the JDK and defined on the spot. i dumped it (with `-Djdk.proxy.ProxyGenerator.saveGeneratedFiles=true`; on jdk 25.0.4 that writes the file and then crashes the program, so it's strictly a debugging trick) and read it with `javap`:

load the handler, load the cached `Method`, box the arguments into an array, call `invoke`, cast the result back. `count()` does the same and then unboxes an `Integer` with `intValue()`. that's why returning the wrong type from a handler is a `ClassCastException` at the call site, and returning `null` from an `int` method is a `NullPointerException`.

## interfaces only

the generated class already extends `java.lang.reflect.Proxy` (that's where the `h` field lives), and a java class gets one superclass. so it can implement as many interfaces as you like, but it can't extend your class. ask for one anyway:

```text
Exception in thread "main" java.lang.IllegalArgumentException: java.util.ArrayList is not an interface
```

when you need to proxy a class, you need a library that generates a *subclass* and overrides each method: ByteBuddy (what Hibernate and Mockito use today) or the older cglib (which Spring repackaged into `spring-core`). subclass proxies can't touch `final` classes or `final` methods, and can't intercept `private` ones, for the same reason a normal subclass can't.

## where you've already used one

| library | what you write | what the proxy does |
| --- | --- | --- |
| Spring Data | `interface UserRepo extends JpaRepository` | parses method names like `findByEmail` into queries |
| Retrofit, Feign | `interface Api { @GET("/users") ... }` | turns each call into an HTTP request |
| MyBatis | a mapper interface | runs the SQL mapped to each method |
| Spring AOP | `@Transactional`, `@Cacheable`, `@Async` on a bean | wraps calls in a transaction, a cache lookup, a thread hop |
| the JDK itself | `@Route(path = "/x")` | answers annotation element calls from a map ([annotations](/learn/meta/annotations)) |

Spring AOP uses a JDK dynamic proxy when the bean implements an interface and class-based proxies otherwise (Spring Boot defaults to class-based for everything). either way the mechanism is the same, and so is the most famous bug in Spring:

<Gotcha title="self-invocation skips the proxy">
annotations like `@Transactional`, `@Cacheable` and `@Async` only work when the call comes in *through the proxy*. a method calling another method on `this` is a plain java call on the target object, so the second method's annotation does nothing. no warning, no error. move the method to another bean, or call it through the injected proxy. (Spring's AspectJ weaving mode rewrites the bytecode of your class instead and doesn't have this problem, at the cost of a build or load-time step.)
</Gotcha>

<Deep title="where the proxy class lives, and default methods">
for interfaces that are all public, the JDK defines the proxy class in a dynamic module made just for proxies: `Runnable`'s proxy came back as `jdk.proxy1.$Proxy0`, in module `jdk.proxy1`. if any interface is package-private, the proxy has to live in that same package and class loader instead, which is why the `Greeter` proxy above was just `$Proxy0`. proxy classes are cached per class loader and interface list, so the second `newProxyInstance` with the same interfaces doesn't generate anything.

a `default` method on the interface also goes to the handler. to run the interface's own default body from inside your handler, call `InvocationHandler.invokeDefault(proxy, method, args)` (java 16+). before that, people needed a private-access `MethodHandles.Lookup` hack.
</Deep>

<Interview q="how does @Transactional work, and why doesn't it work when I call the method from the same class?">
Spring doesn't hand other beans your object, it hands them a proxy: a JDK dynamic proxy if the bean implements an interface, otherwise a generated subclass. the proxy's handler starts a transaction, calls your method on the real object, then commits or rolls back. a call from inside the same class is a call on `this`, which is the real object, not the proxy, so no handler ever runs and the annotation on the inner method has no effect. fix it by calling through another bean (or the injected proxy of yourself), or switch to AspectJ weaving, which modifies the class itself.
</Interview>

<Keylines>
- `Proxy.newProxyInstance` generates a class at runtime that implements your interfaces.
- every call, including `toString`, `equals` and `hashCode`, lands in `InvocationHandler.invoke`.
- unwrap `InvocationTargetException`, return the right type, and never return `null` for a primitive.
- interfaces only. classes need a subclass-generating library like ByteBuddy.
- the advice is in the proxy. `this.method()` goes around it.
</Keylines>
