<InShort>
when something throws, the JVM **unwinds** the stack: it abandons the current method, pops frames one by one, runs any **finally** blocks it passes, and stops at the first `catch` whose type matches. if nothing matches, the thread dies and prints the stack trace.

`finally` runs on every way out of a `try`: normal end, `return`, `break`, or an exception. (almost every way. there's a short list.)
</InShort>

## the picture

an exception is a hot potato handed back down the line of people who called you. each person either catches it, or steps out of the line and passes it on. anyone holding a `finally` gets to tidy their desk on the way out, whether they caught the potato or not.

no frame "returns" during this. nobody gets a return value, no line after the call runs. frames are just thrown away, newest first, until someone has a matching `catch`.

## catch: the first match wins

a `try` can have several `catch` clauses. the JVM checks them top to bottom and runs the first one where the exception `instanceof` the declared type. the rest are skipped.

```java title="Main.java" run output="no such file: missing.txt\nother I/O: IOException\nbad path: InvalidPathException"
import java.io.IOException;
import java.nio.file.*;

void main() {
    for (String name : new String[] {"missing.txt", "", "x\0y"}) {
        try {
            Files.readString(Path.of(name));
        } catch (NoSuchFileException e) {                         // the specific one first
            IO.println("no such file: " + e.getMessage());
        } catch (IOException e) {                                 // then its parent
            IO.println("other I/O: " + e.getClass().getSimpleName());
        } catch (InvalidPathException | UnsupportedOperationException e) {   // multi-catch
            IO.println("bad path: " + e.getClass().getSimpleName());
        }
    }
}
```

(`""` is the current directory, which you can't read as a file. `"x\0y"` has a NUL byte, which no path can contain.)

two compile-time rules come out of "first match wins":

- **specific before general.** put `catch (IOException e)` above `catch (NoSuchFileException e)` and javac refuses, because the second clause could never run.
- **multi-catch alternatives can't be related.** `FileNotFoundException | IOException` is an error too: the parent already covers the child.

```text
error: exception NoSuchFileException has already been caught
error: Alternatives in a multi-catch statement cannot be related by subclassing
```

in a multi-catch, `e` is implicitly `final` and its static type is the closest common supertype (here `RuntimeException`).

## finally: on every way out

<TryPaths />
</Figure>

that's why `finally` is where cleanup goes: releasing a lock, closing a file, restoring some state. (for anything `AutoCloseable` there's something better, [try-with-resources](/learn/core-api/try-with-resources).)

the list of ways `finally` *doesn't* run is short: `System.exit()` (or `Runtime.halt()`) inside the `try`, the JVM crashing or being killed (`kill -9`, the container's OOM killer, power), the `try` never finishing (an infinite loop, a deadlock), and daemon threads, which are simply abandoned when the JVM exits.

<Predict options={["1", "2", "compile error"]} answer={1}>
```java
static int f() {
    try {
        return 1;
    } finally {
        return 2;
    }
}
```
<Explain>
`return 1` evaluates the value and gets ready to leave, but leaving the `try` runs the `finally`, and the `finally` does its own `return 2`. the later return wins. it compiles fine (only `-Xlint` warns: `finally clause cannot complete normally`).
</Explain>
</Predict>

<Predict options={["1", "2"]} answer={0}>
```java
static int g() {
    int x = 1;
    try {
        return x;
    } finally {
        x = 2;
    }
}
```
<Explain>
`return x` copies the *value* of `x` (1) aside before the `finally` runs. changing the variable afterwards doesn't touch the copy. (if `x` were a reference to a mutable object, the `finally` could still change the object it points at. same rule as everywhere in java: [the slot is copied](/learn/basics/pass-by-value).)
</Explain>
</Predict>

<Gotcha title="return in finally eats exceptions">
```java
try {
    throw new IllegalStateException("important");
} finally {
    return -1;   // the exception is gone. no trace, no log, nothing.
}
```
a `return` (or `break`, or `continue`) in a `finally` replaces whatever was in flight, including an exception. the same happens if the `finally` throws: its exception replaces the original one. keep `finally` blocks small, never `return` from them, and don't let them throw.
</Gotcha>

## don't swallow

<Compare>
<Bad label="the silent catch">
```java
try {
    config = load(path);
} catch (Exception e) {
    // TODO
}
```
the program keeps going with `config == null`, and the NPE shows up an hour later, in some other class, with no hint of the real cause.
</Bad>
<Good label="handle it, or let it go">
```java
try {
    config = load(path);
} catch (NoSuchFileException e) {
    config = Config.defaults();   // a real decision
}
// anything else: don't catch it here.
```
catch what you can actually do something about. everything else should keep unwinding to a level that can (and usually that's the top, which logs it).
</Good>
</Compare>

<Deep title="how the JVM finds the catch: the exception table">
there's no "try" instruction in bytecode. instead each method has an **exception table**: rows of "if something is thrown between instruction `from` and `to`, and it's an instance of `type`, jump to `target`". here's `javap -c` (javac 25) for this method:

```java
static void h() {
    try {
        work();
    } catch (IllegalStateException e) {
        log(e);
    } finally {
        cleanup();
    }
}
```

and what's in the `.class` file:

```text
 0: invokestatic  #7    // Method work:()V
 3: invokestatic  #12   // Method cleanup:()V        ← finally, copy 1 (normal path)
 6: goto          26
 9: astore_0                                         ← the catch block
10: aload_0
11: invokestatic  #17   // Method log:(Ljava/lang/Exception;)V
14: invokestatic  #12   // Method cleanup:()V        ← finally, copy 2 (after the catch)
17: goto          26
20: astore_1                                         ← "any": everything else
21: invokestatic  #12   // Method cleanup:()V        ← finally, copy 3
24: aload_1
25: athrow                                           ← rethrow it
26: return
Exception table:
   from    to  target type
       0     3     9   Class java/lang/IllegalStateException
       0     3    20   any
       9    14    20   any
```

two things to see. `finally` isn't a jump target, it's **copied** onto every exit path (three times here). and when a method throws, the JVM searches *that method's* table for a matching row. no match: pop the frame, and search the caller's table at the call site. that's the unwinding from the stepper above, one table lookup per frame. it costs nothing when nothing is thrown.
</Deep>

<Interview q="does finally run if the try block returns?">
yes. `return` evaluates its value first, then the `finally` runs, then the method returns that saved value. a `return` inside the `finally` would override it (and would also swallow an in-flight exception), which is why you never put one there. finally doesn't run after `System.exit()`, if the JVM dies, if the try never completes, or for daemon threads at shutdown.
</Interview>

<Keylines>
- a throw abandons the method. frames are popped until a catch matches.
- catches are checked top to bottom. specific before general, or javac complains.
- finally runs on every way out: normal, return, break, exception.
- never return or throw from a finally. it replaces whatever was in flight.
- catch what you can handle. let the rest unwind.
</Keylines>
