<InShort>
a test is a method with **`@Test`** on it. **JUnit** finds those methods, runs each one on a **fresh instance** of the test class, and reports what passed. JUnit 6 (september 2025) is the current major version and needs java 17+.

around it sits a small standard toolkit: **AssertJ** for assertions that explain themselves, **Mockito** for fake collaborators, and **Testcontainers** for a real database in docker instead of a fake one.
</InShort>

## the picture

a test is a tiny experiment. set up a clean lab bench, do one thing, check the result, throw the bench away. the "throw it away" part is the important one: if experiments share a bench, the second one can pass (or fail) because of crumbs the first one left. junit enforces the clean bench for you, by building a new object for every single test method.

## a first test

the code under test, and its test. it's not runnable on this page (junit isn't part of the JDK), so here's what really happened when i ran it with the junit 6.1.3 console launcher on jdk 25.

```java title="Prices.java"
class Prices {
    static long withTax(long cents) { return cents + cents * 18 / 100; }
}
```

```java title="PricesTest.java"
import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

class PricesTest {

    @ParameterizedTest(name = "{0} cents → {1}")
    @CsvSource({
        "100,  118",
        "0,    0",
        "1000, 1180",
        "99,   117",
    })
    void addsTax(long cents, long expected) {
        assertEquals(expected, Prices.withTax(cents));
    }
}
```

```text title="java -jar junit-platform-console-standalone-6.1.3.jar execute ... --details=tree"
├─ JUnit Jupiter ✔
│  └─ PricesTest ✔
│     └─ addsTax(long, long) ✔
│        ├─ "100" cents → "118" ✔
│        ├─ "0" cents → "0" ✔
│        ├─ "1000" cents → "1180" ✔
│        └─ "99" cents → "117" ✘ expected: <117> but was: <116>
```

one method, four tests, and the fourth found a real bug: `99 * 18 / 100` is `17.82`, and integer division throws away the `.82`. a single hand-picked example (100 cents) would have passed forever. that's the case for **parameterized tests**: the cases are data, so adding the nasty ones costs one line each. `@CsvSource`, `@ValueSource`, `@EnumSource` and `@MethodSource` (any method returning a stream of arguments) cover almost everything.

```java
@Test void first()  { System.out.println("first"); }
```

<Explain>
on junit 6.1.3 this class ran `second` before `first`, every time. the default method order is deterministic (so builds are reproducible) but intentionally *not* source order, so tests that secretly depend on each other break early. if order truly matters (it usually shouldn't), say so with `@TestMethodOrder(MethodOrderer.OrderAnnotation.class)` and `@Order(1)`.
</Explain>

## assertions that explain themselves

when a test fails, the message is the whole bug report. junit's own `assertEquals` tells you the two values. AssertJ's fluent assertions (`assertThat(x).something()`) tell you *how* they differ. here a method meant to return the first three items alphabetically accidentally sorts in reverse. real output from both:

<Compare>
<Bad label="assertEquals on a list">

</Bad>

```text
  ["pear", "kiwi", "fig"]

  ["apple", "fig", "kiwi"]
```

AssertJ has assertions for almost everything (`containsEntry`, `isCloseTo`, `hasMessageContaining`, `extracting(...)`), and your IDE autocompletes them after `assertThat(x).`, which is most of why people like it.

## mocks and spies

some code talks to things you don't want in a unit test: a payment API, a clock, an email server. a **mock** is a fake stand-in you create in one line, tell what to return, and check afterwards. Mockito is the standard one.

<Defs>
<dt>mock</dt><dd>a fake with no real behaviour. unstubbed methods return defaults. use it for collaborators: the thing your code *calls*.</dd>
<dt>spy</dt><dd>a real object, wrapped. real methods run unless you stub them. use it rarely: usually a smell that a class does too much.</dd>

</Defs>

</Gotcha>

## real dependencies: testcontainers

mocking a database is a trap: your fake happily accepts SQL the real postgres would reject. **Testcontainers** starts a real postgres (or kafka, or redis) in docker for the duration of a test, hands you its address, and deletes it afterwards. this is the 2.0 API (artifact `testcontainers-postgresql`, class in `org.testcontainers.postgresql`):

```java title="UserRepositoryTest.java"
import org.junit.jupiter.api.Test;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.postgresql.PostgreSQLContainer;

@Testcontainers
class UserRepositoryTest {

    @Container
    static PostgreSQLContainer db = new PostgreSQLContainer("postgres:17-alpine");

    @Test
    void savesAndLoads() throws Exception {
        try (var conn = java.sql.DriverManager.getConnection(
                db.getJdbcUrl(), db.getUsername(), db.getPassword())) {
            // run real migrations, real queries, real constraints
        }
    }
}
```

the trade: these tests take seconds instead of milliseconds and need docker on the build machine. that's why most suites are mostly fast unit tests with mocks, plus a smaller layer of these.

<Deep title="what changed in junit 6">
junit 6.0.0 shipped on september 30, 2025. the big moves: java 17 is the minimum (kotlin 2.2 for kotlin users), the platform, jupiter and vintage artifacts now share one version number (no more "platform 1.13 + jupiter 5.13"), and every module is annotated with JSpecify nullness annotations (more on those in [code quality](/learn/tooling/code-quality)). the vintage engine that runs junit 4 tests is deprecated, so a junit 4 suite should migrate rather than ride along. test code written for junit 5 mostly compiles unchanged: same `org.junit.jupiter.api` package, same annotations.
</Deep>

<Interview q="why does junit create a new instance of the test class for every test method?">
isolation. instance fields are reset for every test, so one test can't leave state behind that makes another pass or fail. that's also why `@BeforeAll` and `@AfterAll` must be static: they run when no instance exists. bonus point: you can switch to one instance per class with `@TestInstance(Lifecycle.PER_CLASS)` (then `@BeforeAll` can be non-static), and static fields are always shared, so they're the place leaks come from.
</Interview>

<Keylines>
- `@Test` methods, each on a fresh instance. statics are the only thing shared.
- parameterized tests make the nasty cases cheap. the 99 cents case found the bug.
- test order is fixed but not source order. tests shouldn't care.
- AssertJ messages explain the diff. mocks fake collaborators, spies wrap real objects.
- for databases, test against a real one in docker with Testcontainers.
</Keylines>
