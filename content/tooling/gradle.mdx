<InShort>
gradle turns your build into a **graph of tasks**. you ask for one task, gradle runs only the tasks it depends on, in order, and **skips every task whose inputs haven't changed** since last time.

the build script is real code (kotlin, usually), it runs in three **phases**: initialization, configuration, execution. knowing which phase a line runs in is most of the battle.
</InShort>

## the picture

maven is an assembly line: fixed stations, always in the same order. gradle is a kitchen with a recipe graph. to serve dinner you need pasta and sauce, the sauce needs chopped onions, the pasta needs boiling water. ask for "sauce" and only the onions and the sauce happen. and if the onions you chopped yesterday are still in the fridge, unchanged, nobody chops them again.

that "still in the fridge" check is the whole trick. every task declares its **inputs** (source files, classpath, settings) and **outputs** (class files, a jar). gradle fingerprints both. same inputs, outputs still there: `UP-TO-DATE`, skipped.

## a build script

this is a complete build for a small app with one library and junit. gradle 9.8.1 built it on jdk 25. the kotlin DSL (`build.gradle.kts`) is what `gradle init` generates by default now; the older groovy DSL (`build.gradle`) still works.

```kotlin title="build.gradle.kts"
plugins {
    application                         // java + a run task + start scripts + zips
}

group = "com.acme"
version = "1.0"

repositories {
    mavenCentral()
}

dependencies {
    implementation("com.google.guava:guava:33.7.2-jre")
    testImplementation("org.junit.jupiter:junit-jupiter:6.1.3")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)   // compile + test with a JDK 25
    }
}

application {
    mainClass = "com.acme.app.App"
}

tasks.test {
    useJUnitPlatform()
}
```

it uses the same directory layout as maven (`src/main/java`, `src/test/java`) and the same repositories. the difference is what happens when you run it.

<Quiz question="you change the body of a private method in App.java. which of these does gradle NOT rerun on the next build?" options={["compileJava", "test", "compileTestJava", "jar"]} answer={2}>
<Explain>
`compileJava` reruns (its input changed), so `jar` does too, and `test` reruns because the classes under test changed. but `compileTestJava` only depends on App's **ABI**: its public signatures. a body change leaves the ABI identical, so the tests don't need recompiling. gradle calls this compile avoidance. add a public method and it reruns.
</Explain>
</Quiz>

## three phases, and why it matters

a gradle build always runs in the same three phases:

<Figure caption="hover a phase. the configuration phase runs on every single build, even when every task ends up UP-TO-DATE.">
<Flow
  stages={[
    { label: "initialization", sub: "settings.gradle.kts", note: "which projects are in this build? (one, or a multi-project tree)" },
    { label: "configuration", sub: "build.gradle.kts", note: "runs the build scripts top to bottom. builds the task graph. no task actions yet." },
    { label: "execution", sub: "doLast { }", note: "runs the actions of the tasks the target needs, in dependency order, skipping up-to-date ones." },
  ]}
/>
</Figure>

you can watch it happen with a few `println`s:

```kotlin title="build.gradle.kts"
println("2. build.gradle.kts: configuration")

tasks.register("hello") {
    println("3. configuring hello")       // configuration phase
    doLast {
        println("4. running hello")       // execution phase
    }
}

tasks.register("other") {
    println("configuring other")          // never printed
}
```

```bash
$ gradle hello -q
1. settings.gradle.kts: initialization
2. build.gradle.kts: configuration
3. configuring hello
4. running hello
$ gradle help -q
1. settings.gradle.kts: initialization
2. build.gradle.kts: configuration
```

notice `configuring other` never shows up, and `hello` isn't even configured when you run `help`. `tasks.register` is lazy: a task's configuration block only runs if that task ends up in the graph.

<Gotcha title="work in the configuration block runs every time">
code in a task's block but outside `doLast { }` runs during configuration. so `tasks.register("deploy") { exec { ... } }` doesn't deploy when you run `deploy`, it deploys whenever *anything* causes `deploy` to be configured, and then `doLast` does nothing. real work goes in `doLast` (or a proper task class with declared inputs and outputs). the configuration phase should only describe.
</Gotcha>

## dependencies and configurations

gradle's version of maven scopes is the **configuration** (overloaded word, sorry). the ones you'll use:

| configuration | on the compile classpath | at runtime | maven equivalent |
| --- | --- | --- | --- |
| `implementation` | yes | yes | `compile`, but not leaked to your consumers' compile classpath |
| `api` (`java-library` plugin) | yes, and your consumers' too | yes | `compile` |
| `compileOnly` | yes | no | `provided` |
| `runtimeOnly` | no | yes | `runtime` |
| `testImplementation` | tests only | tests only | `test` |

and here's a real difference from maven. same two libraries as [the maven chapter](/learn/tooling/maven), json-lib wanting text-utils 1.0 and http-lib wanting 2.0:

```bash
$ gradle dependencies --configuration runtimeClasspath
runtimeClasspath - Runtime classpath of source set 'main'.
+--- com.acme:json-lib:1.0
|    \--- com.acme:text-utils:1.0 -> 2.0
\--- com.acme:http-lib:2.0
     \--- com.acme:core-lib:2.0
          \--- com.acme:text-utils:2.0
```

gradle picked **2.0**, the highest version, and the `1.0 -> 2.0` arrow tells you it overrode a request. maven picked 1.0 (nearest) and the app crashed with `NoSuchMethodError`. neither rule is always right: highest-wins can also break things if 2.0 removed something 1.0 had. but at least you know which rule you're living with.

## the speed stack

why gradle builds get faster the more you run them:

<Defs>
<dt>up-to-date checks</dt><dd>skip a task whose input and output fingerprints match the last run. on by default. the figure above.</dd>
<dt>the daemon</dt><dd>a long-lived background JVM that keeps the build model and a warmed-up JIT between builds. on by default.</dd>
<dt>build cache</dt><dd>reuse a task's outputs from <em>any</em> earlier build with the same inputs, even another branch or another machine (with a remote cache). `--build-cache` or `org.gradle.caching=true`.</dd>
<dt>configuration cache</dt><dd>skip the whole configuration phase when nothing in the build scripts changed. gradle 9 recommends it ("Consider enabling configuration cache to speed up this build", it printed) but still doesn't turn it on for you.</dd>
</Defs>

<Deep title="the wrapper, and toolchains">
commit `gradlew`, `gradlew.bat` and `gradle/wrapper/` to the repo. `./gradlew build` downloads exactly the gradle version the project pins, so a fresh clone never needs gradle installed and everyone builds with the same one. toolchains (the `java { toolchain { } }` block) do the same for the JDK: gradle itself might run on jdk 21 while compiling and testing your code with jdk 25. it finds installed JDKs on its own, and with a toolchain resolver plugin (foojay's is the common one) it can download a missing one.
</Deep>

<Interview q="what's the difference between implementation and api in gradle?">
both put the library on your compile and runtime classpath. `api` also puts it on the *compile* classpath of everyone who depends on you, because its types appear in your public API. `implementation` keeps it private: consumers get it at runtime but can't compile against it, so changing it doesn't force them to recompile. default to `implementation`, use `api` (from the `java-library` plugin) only when your public method signatures mention the library's types. it's the same idea as `requires transitive` in [modules](/learn/tooling/modules).
</Interview>

<Keylines>
- gradle runs a graph of tasks, only the ones your target needs.
- every task fingerprints its inputs and outputs. unchanged = UP-TO-DATE, skipped.
- a body-only change skips recompiling the tests: compile avoidance.
- configuration runs every build. real work goes in `doLast`.
- version conflicts: gradle picks the highest, maven picks the nearest.
</Keylines>
