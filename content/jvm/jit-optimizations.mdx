<InShort>
C2's big moves are a short list. **inlining** pastes small methods into their callers. that unlocks **escape analysis** (objects that never leave the method don't get allocated at all), loop tricks (**unrolling**, **range check elimination**, **vectorization**), and **intrinsics** (hand-written machine code for methods like `System.arraycopy`). and all of it rests on **speculation**: C2 bets on what the profile saw, and **deoptimizes** when a bet loses.
</InShort>

## the picture

you know how people say "the JIT will optimize that away"? sometimes it does, sometimes it really doesn't, and the difference is almost always one thing: whether the code got inlined.

think of a chef who writes the recipe for a dish in terms of other recipes: "make the sauce (see page 40)". following it literally means flipping back and forth. an experienced chef first copies page 40 into the recipe, and only *then* notices that half the sauce steps are wasted for this dish. inlining is the copying. every other optimization is the noticing, and it can only notice what's on the page.

## what decides inlining

C2 inlines a call when it's both possible and worth it. possible: the target must be known. for a static, private, final or constructor call it always is. for a virtual or interface call, C2 uses the **type profile** from tier 3:

```text title="-XX:+PrintInlining, the same call site with 1, 2 and 3 receiver classes"
@ 27   Mega$Circle::area (14 bytes)   inline (hot)
       \-> TypeProfile (40960/40960 counts) = Mega$Circle

@ 27   Mega$Circle::area (14 bytes)   inline (hot)
@ 27   Mega$Square::area (10 bytes)   inline (hot)
       \-> TypeProfile (20480/40960 counts) = Mega$Square
       \-> TypeProfile (20480/40960 counts) = Mega$Circle

@ 27   Mega$Shape::area (0 bytes)   failed to inline: virtual call
```

one class (monomorphic): inline it behind a cheap class check. two (bimorphic): inline both, check which one you have. three or more (megamorphic): give up and do a real vtable or itable call. here's the loop `for (Shape s : shapes) t += s.area()` over 4096 shapes, each run in a fresh JVM:

<Figure caption="one call site, 1 to 4 receiver classes, median of three runs, jdk 25 on an M4 Pro. the cliff is between 2 and 3.">
<MeasuredBars unit="ns/call" data={[
  { label: "1 class (monomorphic)", value: 0.69, tone: "live" },

worth it: methods under `MaxInlineSize` = 35 bytes of bytecode are inlined even when they aren't hot, hot ones up to `FreqInlineSize` = 325 bytes, nested at most `MaxInlineLevel` = 15 deep, and not if the callee is already compiled into a big chunk of machine code (`InlineSmallCode`). that's why small methods are good for performance, not bad: they're exactly what inlining loves.

## loops

hot code is mostly loops, and C2 has a bag of tricks for them. **range check elimination**: `a[i]` normally checks `0 <= i < a.length` every time; when `i` runs from 0 to `a.length`, C2 proves the checks can't fail and hoists them out of the loop. **unrolling**: do several iterations per trip around the loop, so the loop's own overhead (compare, jump, increment) is paid less often. **vectorization** (C2 calls it SuperWord): turn several iterations into single SIMD instructions that work on 4 or 8 ints at once.

here's `b[i] = a[i] + c[i]` over 4096 ints, turning each trick off in turn:

<Deep title="loop strip mining, and why your loops still have safepoint polls">
a counted `int` loop compiled by C2 used to have no safepoint poll inside it at all, so a long loop could hold up a GC pause for its whole duration. since java 10, C2 splits such loops into an outer loop with a poll and an inner loop of at most `LoopStripMiningIter` = 1000 iterations without one (that's on by default when the collector cares about pause times, which includes G1). more in [safepoints](/learn/jvm/safepoints).
</Deep>

## intrinsics

some JDK methods are never compiled from their bytecode at all. the JVM recognizes them by name and drops in hand-written machine code instead. `PrintInlining` marks them:

```text title="-XX:+PrintInlining (excerpt)"
@ 25   java.lang.Integer::bitCount (53 bytes)   (intrinsic)
@ 1    java.lang.Math::sqrt (5 bytes)   (intrinsic)
@ 11   java.lang.System::arraycopy (0 bytes)   (intrinsic)
@ 44   java.lang.StringLatin1::equals (36 bytes)   (intrinsic)
```

`Integer.bitCount` is 53 bytes of clever bit-twiddling in `Integer.java`, but on this machine C2 uses the CPU's population-count instruction instead. counting bits over a 4096-int array took 0.12 ns per element normally and 0.25 ns with `-XX:DisableIntrinsic=_bitCount_i`. there are hundreds of intrinsics: `System.arraycopy`, string comparisons and searches, `Math` functions, CRC32, AES and SHA, `Object.hashCode`, `Thread.currentThread`. the practical upshot: use the JDK method instead of hand-rolling it. yours won't be intrinsified.

## speculation and deoptimization

everything above is a bet. "this call site only ever sees `Circle`" is true *so far*. C2 compiles as if it's always true, with a cheap check that falls off a cliff if it isn't: an **uncommon trap**. when a trap fires, the JVM throws away the compiled code (marks it *not entrant*), rebuilds an interpreter frame from the compiled frame's state, and continues in the interpreter. later, with a better profile, it compiles again.

here's a real one. the call site in `area` sees 200,000 `Circle`s, then one `Square`:

```java title="Deopt.java"
static double area(Shape s) {
    return s.area();
}
// phase 1: area(new Circle(i)) 200,000 times
// phase 2: area(new Square(2)), then a mix of both
```

```text title="java -XX:+PrintCompilation -Xlog:deoptimization=debug Deopt (area only)" {3,5,6}
14   21       4       Deopt::area (7 bytes)
phase 2: a square shows up
[0.017s][debug][deoptimization] cid=21 level=4 Deopt.area(LDeopt$Shape;)D trap_bci=1 class_check maybe_recompile
17   21       4       Deopt::area (7 bytes)   made not entrant: uncommon trap
17   25       4       Deopt::area (7 bytes)
```

deoptimization is what makes aggressive optimization safe. C2 can assume a branch is never taken, a class has no subclasses (class hierarchy analysis), or a value is never null, because being wrong costs a recompile instead of a wrong answer. the price shows up as occasional hiccups when a program changes phase.

<Gotcha title="the warmup lie">
benchmarks that warm up on one kind of input and then measure another measure something that doesn't exist in production. warm up `area()` with only circles, and you're timing an inlined, monomorphic call. in production, where three shape types flow through, that call site is megamorphic and over twice as slow. profiles are per call site and they're real: feed your benchmark realistic data, and use [JMH](/learn/performance/jmh), which forks a fresh JVM per benchmark so one test's profile can't pollute another's.
</Gotcha>

<Interview q="what is escape analysis, and does it mean java allocates objects on the stack?">
escape analysis is C2 working out, after inlining, whether an object can be seen outside the method being compiled (returned, stored in a field or array, passed somewhere it can't see). if it can't, HotSpot doesn't move it to the stack: it removes the object entirely and keeps its fields as separate values in registers or stack slots (scalar replacement). it can also drop locks on objects that never escape (lock elision). it only works on what's been inlined, so it fails quietly when a method is too big to inline or the call is megamorphic.
</Interview>

<Keylines>
- inlining first. almost every other optimization needs it.
- objects that don't escape aren't allocated at all. 72 bytes and 6 ns became 0 and 0.4 here.
- call sites with 1 or 2 receiver classes inline. 3 or more don't.
- loops get bounds checks hoisted, unrolled and vectorized: 12x over C1 for a simple loop.
- it's all speculation. a broken bet means an uncommon trap and a recompile, not a wrong answer.
</Keylines>
