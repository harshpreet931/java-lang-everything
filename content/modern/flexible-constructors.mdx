<InShort>
since java 25 (JEP 513), a constructor can run statements **before** `super(...)` or `this(...)`. that part is the **prologue**: it can validate arguments, compute values for the superclass constructor, and assign its own fields, all before any superclass code runs.

what it still can't do is touch the object: no reading fields, no calling instance methods, no passing `this` anywhere. the object isn't built yet, and the compiler makes sure nobody finds out.
</InShort>

## the picture

you know the rule "`super(...)` must be the first statement in a constructor"? it was there from java 1.0, and it made simple things awkward. want to check an argument before handing it to the superclass? you couldn't, so you wrote a static helper and called it inside the `super(...)` arguments, or you let the superclass do work with a bad value and threw afterwards.

think of building a house. the old rule said the foundation crew (the superclass) has to start before you've even looked at the plans: you can't check the plot, can't measure anything, just pour concrete and hope. the new rule lets you survey the land and check the permits first, as long as you don't try to move furniture into a house that doesn't exist yet.

<Compare>
<Bad label="before java 25: logic squeezed into a static helper">

```java
class Employee extends Person {
    Employee(String rawName) {
        super(clean(rawName));

        if (raw == null || raw.isBlank())
            throw new IllegalArgumentException("no name");
        return raw.strip().toUpperCase();
    }
}
```
</Bad>
<Good label="java 25: just write it in order">
```java
class Employee extends Person {
    Employee(String rawName) {
        if (rawName == null || rawName.isBlank())

        String name = rawName.strip().toUpperCase();
        super(name);
```

</Good>

## prologue and epilogue

with statements allowed before `super(...)`, a constructor has two halves. the prologue runs before the superclass is constructed, the epilogue after. across a hierarchy that gives a neat order: prologues run from the subclass **up**, epilogues from the top **down**:

## what the prologue still can't do

the object is allocated (memory, zeroed fields) but not constructed, so anything that could observe it is off limits. every one of these is rejected by javac 25:

| in the prologue | javac 25 says |
| --- | --- |
| read a field: `int y = a;` | `cannot reference a before supertype constructor has been called` |
| call an instance method: `hashCode();` | `cannot reference hashCode() before supertype constructor has been called` |
| use `this`: `System.out.println(this);` | `cannot reference this before supertype constructor has been called` |
| call a superclass method: `super.m();` | `cannot reference super before supertype constructor has been called` |
| assign a field that has an initializer | `cannot assign initialized field 's' before supertype constructor has been called` |
| `return;` | `'return' not allowed before explicit constructor invocation` |
| `if (b) super(1); else super(2);` | `explicit constructor invocation not allowed here` |

what *is* allowed: locals, arguments, static methods and fields, throwing, and assigning your own fields that don't have an initializer. a lambda in the prologue counts as touching `this` if it mentions a field, so that's out too.

<Gotcha title="the prologue runs before the superclass checks anything">
moving validation into the prologue changes *when* it runs: before the superclass constructor, not after. usually that's what you want (fail before doing work). but if the superclass constructor itself validated or normalized an argument you're now inspecting, your check sees the raw value. and the other way round: a field you set in the prologue is visible to superclass code, which is exactly the point, so set it to something valid.
</Gotcha>

<Deep title="why the old rule existed, and why it could go">
the JVM never required `super(...)` to come first. its rules are looser: on every code path the superclass constructor is called exactly once (and not inside a `try`), and until then the half-built object is off limits except for assigning fields. javac itself has always relied on that, for instance to store the hidden outer-instance field of an inner class before calling `super`. the "first statement" rule was the language being stricter than the JVM, because "first" was easy to check and guaranteed "not used". JEP 513 swaps it for the real requirement, checked in what the spec now calls an *early construction context*, and needed no JVM change at all. it previewed three times: as "statements before super(...)" (JEP 447, java 22), as "flexible constructor bodies" with early field assignment (JEP 482, 23, and JEP 492, 24), and went final unchanged in java 25.
</Deep>

<Interview q="what are flexible constructor bodies?">
java 25 lets a constructor have statements before its explicit `super(...)` or `this(...)` call. that prologue can validate arguments, compute the arguments for the superclass constructor, and initialize the class's own fields (ones without initializers), but it can't use the instance: no field reads, no instance method calls, no `this`, no `super.x`. prologues run bottom-up through the hierarchy, epilogues top-down. the practical wins are fail-fast validation without static helpers, and setting subclass fields before a superclass constructor can call an overridden method and see their default values. JEP 513, final in 25.
</Interview>

<Keylines>
- java 25: statements may come before `super(...)` or `this(...)`.
- the prologue validates, prepares arguments, and may assign its own uninitialized fields.
- it can't touch the object: no field reads, no instance methods, no `this`, no `super.x`.
- prologues run subclass-first, epilogues superclass-first.
- set fields in the prologue and an overridden method called by the superclass sees real values.
</Keylines>
