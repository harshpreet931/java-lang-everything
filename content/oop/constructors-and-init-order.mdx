<InShort>
`new Child()` runs things in a fixed order. first, **static init** for `Parent`, then `Child` (once per class, ever). then the object is allocated with every field zeroed. then the constructors **chain up** through `this(...)` and `super(...)` to `Object`, and on the way back down each class runs its **field initializers and init blocks**, then the rest of its constructor body.

parents first. always.
</InShort>

## the picture

you know how a subclass constructor can't touch anything until `super(...)` returns? there's a reason, and it's the order.

think of a two-storey house. you hire the contractor for the top floor (`Child`), but the first thing he does is call the ground-floor contractor (`Parent`) and wait. the ground floor gets finished completely (its fields, its init blocks, its constructor body) before anyone lays a single brick upstairs. the top-floor contractor got called first and walks out last.

## constructors, quickly

a constructor has the class's name and no return type. it's not really a method: you can't call it on an object, only through `new`, `this(...)` or `super(...)`.

```java title="Point.java"
class Point {
    final int x, y;

    Point(int x, int y) {   // the real one
        this.x = x;
        this.y = y;
    }

    Point() {
        this(0, 0);         // delegate to the real one
    }
}
```

<Defs>
<dt>this(...)</dt><dd>call another constructor of the same class. handy for defaults: every path ends up in one "real" constructor.</dd>
<dt>super(...)</dt><dd>call the parent's constructor. if you don't write either, javac quietly inserts <code>super()</code>.</dd>
<dt>default constructor</dt><dd>if a class declares no constructor at all, javac adds a no-arg one that just calls <code>super()</code>. declare any constructor and you lose it.</dd>
<dt>init block</dt><dd>a bare <code>{"{ ... }"}</code> in the class body. runs for every object, as if pasted into each constructor that calls <code>super(...)</code>.</dd>
<dt>static block</dt><dd><code>static {"{ ... }"}</code>. runs once, when the class is initialized.</dd>
</Defs>

<Gotcha title="declaring a constructor deletes the free one">
`Animal` below has no no-arg constructor anymore, and `Dog()` silently calls `super()`. so `Dog` doesn't compile, even though you never wrote a call to anything.

```java title="Main.java"
class Animal {
    String name;
    Animal(String name) { this.name = name; }
}

class Dog extends Animal {
    Dog() { } // [!code error]
}
```

`error: constructor Animal in class Animal cannot be applied to given types;`
</Gotcha>

<Deep title="where the initializers actually go">
there's no "run the initializers" step in the JVM. javac pastes field initializers and init blocks into every constructor that calls `super(...)`, right after that call. constructors that start with `this(...)` don't get a copy, which is why the initializers run once per object, not once per constructor. `javap -c Child` on the program above:

```text nolines
Child();
   aload_0
   ldc "rex"
   invokespecial Child.<init>(String)   // this("rex"). no initializers here
   ldc "Child() body" ...

Child(java.lang.String);
   aload_0
   invokespecial Parent.<init>()        // super()
   ldc "Child field" ... putfield cf    // the field initializer, pasted in
   ldc "Child init block" ...           // the init block, pasted in
   ldc "Child(String) body" ...
```

static initializers get the same treatment, collected in source order into one hidden method called `<clinit>`, which the JVM runs when the class is first initialized. more in [class loading](/learn/jvm/class-loading).
</Deep>

## the trap: overridable calls in a constructor

the parent's constructor runs before the child's fields are set. so if the parent calls a method the child overrides, the child's code runs against a half-built object.

```java title="Main.java" run output="a pet named null"
class Base {
    Base() {
        describe(); // runs Pet's version, before Pet is ready
    }

    void describe() {
        IO.println("a base");
    }
}

class Pet extends Base {
    final String name;

    Pet(String name) {
        this.name = name; // too late: super() already ran
    }

    @Override
    void describe() {
        IO.println("a pet named " + name);
    }
}

void main() {
    new Pet("rex");
}
```

`name` is `final` and it still prints `null`. you just watched a final field change value. kinda cursed.

<Effective item={19} title="design and document for inheritance or else prohibit it">
a constructor shouldn't call methods that subclasses can override, directly or indirectly. the override runs before the subclass constructor, so it sees default values. same goes for `clone` and `readObject`.
</Effective>

### java 25: statements before super()

since <Since v={25} /> a constructor can run code *before* `super(...)` ([flexible constructor bodies](/learn/modern/flexible-constructors), JEP 513). you still can't read `this`, call instance methods or touch `super` there, but you *can* assign your own fields. so the fix is to set `name` first:

```java title="Main.java" run output="a pet named rex" {16-17}
class Base {
    Base() {
        describe();
    }

    void describe() {
        IO.println("a base");
    }
}

class Pet extends Base {
    final String name;

    Pet(String name) {
        this.name = name; // before super(): allowed since java 25
        super();
    }

    @Override
    void describe() {
        IO.println("a pet named " + name);
    }
}

void main() {
    new Pet("rex");
}
```

the prologue is also the right place for validation (throw before the parent does any work). what it can't do is *read* the object:

```java title="Main.java"
class Dog extends Animal {
    String tag = "dog";

    Dog(String name) {
        IO.println(tag); // [!code error]
        super(name);
    }
}
```

`error: cannot reference tag before supertype constructor has been called`

<Interview q="in what order is a subclass object initialized?">
static initializers of the superclass, then the subclass, the first time the class is used. then allocation with all fields zeroed. then the constructor chain: each constructor's first job is `this(...)` or `super(...)`, all the way up to `Object`. on the way back down, each class runs its field initializers and instance init blocks in source order, then the rest of its constructor body. the follow-up is always "so what happens if the superclass constructor calls an overridden method?", and the answer is: it sees the subclass's fields at their defaults.
</Interview>

<Keylines>
- static init runs once per class, parent before child, on first use.
- the object exists, all zeroed, before any constructor code runs.
- constructors chain up first (`this(...)`, `super(...)`), then do their work on the way back down.
- field initializers and init blocks run right after `super(...)` returns, in source order.
- never call an overridable method from a constructor. in java 25 you can at least set your fields before `super()`.
</Keylines>
