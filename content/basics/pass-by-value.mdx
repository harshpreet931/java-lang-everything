<InShort>
java **always** passes arguments **by value**: the method gets a **copy** of whatever is in the caller's variable. for a primitive, that's a copy of the number. for an object, the variable holds a **reference**, so the method gets a copy of the reference: it can change the object both arrows point at, but it can never make the caller's variable point somewhere else.
</InShort>

## the picture

you know how a method can change an object you pass it, but can't swap two ints? people explain that as "primitives by value, objects by reference". it's a tempting story, and it's wrong. there's one rule, and it covers both.

think of a house and its address on a slip of paper. passing a variable to a method is photocopying the slip and handing over the copy. the method can drive to the house and repaint it (you'll see the new paint, it's the same house). it can scribble a different address on its photocopy. that changes nothing on your slip. your slip still says where your house is.

three methods, three experiments. `swap` gets two ints, `fill` changes an object's field, `replace` points its parameter at a new object.

- **`swap(x, y)`**: `a` and `b` are copies of 1 and 2. swapping copies swaps copies.
- **`fill(box)`**: `b` is a copy of the reference. copy or not, it leads to the same `Box`, and `b.value = 99` changes that `Box`.

## what "by reference" would mean

"pass by reference" is a real thing in other languages: the parameter isn't a copy at all, it's another name for the caller's variable. C++ has it (`int&`), C# has it (`ref`). java doesn't, for anything.

</Explain>

```java
void reset(int[] arr) {
    arr[0] = 99;
    arr = new int[0];
}

void main() {
    int[] nums = {1, 2, 3};
    reset(nums);
    IO.println(Arrays.toString(nums));
}
```
<Explain>
`[99, 2, 3]`. both moves in one method. `arr[0] = 99` follows the copied reference to the shared array, so `nums` sees it. `arr = new int[0]` re-points only the copy, so `nums` doesn't. same as `fill` then `replace`.
</Explain>
</Predict>

## so how do you "return" more than one thing?

since a method can't reassign the caller's variables, you hand results back instead:

```java title="Main.java" run output="2 1"
record Pair(int first, int second) {}

Pair swap(int a, int b) {
    return new Pair(b, a);
}

void main() {
    var p = swap(1, 2);
    IO.println(p.first() + " " + p.second());
}
```

return a value (or a small [record](/learn/modern/records) holding several), and let the caller decide what to assign. it's also easier to read: you can see the change happening at the call site. the "mutate an object you were passed" style works too, and the JDK uses it (`Arrays.sort(a)`), but it's easy to surprise people with. [immutability](/learn/oop/immutability) is the story of avoiding those surprises.

<Gotcha title="final parameters don't make the object final">
`void fill(final Box b)` stops the method from re-pointing `b` (`b = new Box(-1)` won't compile), but `b.value = 99` still works: `final` locks the slot, not the object it points to. same for `final` fields and `final` locals. it's a promise about the arrow, never about the thing at the end of it.
</Gotcha>

<Interview q="is java pass-by-value or pass-by-reference?">
always pass-by-value. the subtlety is what the value is: for object types, the variable holds a reference, so the method receives a copy of that reference. through it, the method can mutate the shared object, which looks like pass-by-reference. but assigning a new object to the parameter only changes the method's copy, and the caller's variable never moves, which is the actual test: you can't write a `swap(a, b)` in java that swaps the caller's variables. the JLS describes method invocation as initializing fresh parameter variables with the argument values.
</Interview>

<Keylines>
- java passes everything by value: the parameter is a new variable holding a copy.
- for objects, the copy is a copy of the reference. both arrows lead to one object.
- changing the object through the parameter is visible to the caller.
- re-pointing the parameter (`param = new ...`) never is.
- want more than one result? return it, in a record if needed.
</Keylines>
