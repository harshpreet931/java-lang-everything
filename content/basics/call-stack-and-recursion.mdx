<InShort>
every method call pushes a **frame** onto the **call stack**, and every return pops one: last in, first out. **recursion** is a method calling itself, which works because each call gets its own frame. it needs a **base case** to stop, and java will **not** turn deep recursion into a loop for you, so very deep recursion ends in `StackOverflowError`.
</InShort>

## the picture

a stack of plates. you can only put a plate on top, and only take the top one off. a method call puts a plate on (with that call's local variables written on it), and returning takes it off. whatever plate is on top is the method running right now. everything underneath is paused, waiting.

recursion is when the method on top calls *itself*: another plate, same recipe, its own copy of the variables. the plates keep piling up until some call can answer without calling again (the **base case**), and then they come off one by one, each finishing the work it paused.

## the two rules

every recursive method needs both:

1. **a base case** that returns without recursing (`if (n <= 1) return 1;`).
2. **progress**: each recursive call must get closer to the base case (`factorial(n - 1)`, not `factorial(n)`).

break either rule and the calls never stop. the stack is a fixed-size block of memory (1 to 2 MB per thread by default, depending on the platform, and `-Xss` changes it), so eventually there's no room for the next frame:

```text
Exception in thread "main" java.lang.StackOverflowError
	at Main.factorial(Main.java:6)
	at Main.factorial(Main.java:6)
	at Main.factorial(Main.java:6)
	...
```

how deep you can go before that depends on the frame size and the JIT, more than on your code. [stack and heap](/learn/basics/stack-and-heap#when-the-stack-runs-out) has a meter you can drag to the edge.

## recursion trees and repeated work

some problems split into two smaller copies of themselves, so the calls form a tree. fibonacci is the classic: `fib(n) = fib(n - 1) + fib(n - 2)`.

```java
static long fib(int n) {
    if (n < 2) return n;
    return fib(n - 1) + fib(n - 2);
}
```

## java doesn't optimize tail calls

a call is a **tail call** when it's the very last thing a method does: `return countDown(n - 1);`. some languages notice that the current frame isn't needed anymore and reuse it, so tail recursion runs in constant stack space. java doesn't. every call gets a new frame, tail position or not:

```java title="Main.java"
public class Main {
    static int depth = 0;
    static long countDown(long n) {
        depth++;
        if (n == 0) return 0;
        return countDown(n - 1); // a tail call. java still pushes a frame.
    }
    public static void main(String[] args) {
        try {
            countDown(1_000_000);
        } catch (StackOverflowError e) {
            System.out.println("StackOverflowError after " + depth + " calls");
        }
    }
}
```

```bash
$ java Main.java
StackOverflowError after 32710 calls
```

(32,606 on the next run: the exact depth wobbles with JIT timing.) if the recursion can be millions deep (walking a long linked list, processing a big file line by line), write it as a loop. a loop needs one frame no matter how many times it goes around.

<Gotcha title="recursion depth is input-controlled">
a recursive parser, tree walker or JSON reader works fine in every test, then gets a document nested 50,000 levels deep and dies with `StackOverflowError`. if the depth comes from input you don't control, either use an explicit stack (an `ArrayDeque` you push and pop yourself, on the heap) or put a depth limit in and reject anything deeper.
</Gotcha>

<Deep title="why no tail call optimization?">
HotSpot never did it, and the language has no way to ask for it. a long-cited reason is that parts of the JDK look at the call stack (stack traces, and APIs that ask "who called me?"), and silently removing frames would change what they see. a stack trace with half its frames missing would also be miserable to debug. so if you want constant-space iteration in java, you write a loop. (kotlin's `tailrec` keyword does exactly that conversion at compile time, on the same JVM.)
</Deep>

<Interview q="what happens on the stack when a recursive method runs?">
each call pushes a new frame holding that call's parameters, locals and the point to resume at in the caller. the calls pile up until one hits the base case and returns, then the frames pop in reverse order, each finishing the work it paused (like the `n *` in factorial). stack space used is proportional to the maximum depth, not the total number of calls, which is why naive fibonacci is slow (exponential calls) but never overflows (depth n), and a simple countdown to a million overflows (depth a million) even though it does trivial work.
</Interview>

<Keylines>
- every call pushes a frame, every return pops one. the top frame is what's running.
- recursion works because each call has its own frame and its own copy of the locals.
- a base case to stop, and progress toward it, every time.
- work after the recursive call happens during unwinding, in reverse order.
- java never optimizes tail calls. deep recursion overflows, a loop doesn't.
</Keylines>
