<InShort>
every method call gets a **frame** on the **stack** for its local variables. every object lives on the **heap**. a variable of an object type holds a **reference**, an arrow to the object, never the object itself.

that's the whole chapter. the rest is pictures.
</InShort>

## the picture

you know how `int b = a` makes a copy, but `Point q = p` somehow doesn't? that's because there are two kinds of memory in play, and the variable only ever holds what fits in its own little slot.

think of a coat check. the heap is the cloakroom (where the coats actually are). a reference is the ticket in your pocket. you can photocopy the ticket as many times as you want and there's still one coat. lose every ticket and the coat just sits there until staff clears it out (that's the garbage collector).

## what lives where

| thing | where it lives |
| --- | --- |
| a local primitive (`int n = 3`) | in the frame, on the stack |
| a local reference (`Point p`) | the reference is in the frame. the object is on the heap |
| every object, every array | the heap. always. no exceptions in the language |
| fields, even `int` ones | inside their object, so on the heap |
| `static` fields | with the class, which the JVM keeps on the heap too |
| method parameters | in the callee's frame, as copies (more in [pass-by-value](/learn/basics/pass-by-value)) |
| string literals | on the heap, deduplicated in the [string pool](/learn/deep-dives/string-pool) |

<Gotcha title="locals don't get defaults, fields do">
an object's memory is zeroed when it's allocated, so an unset `int` field is `0` and an unset reference field is `null`. a frame's slots aren't zeroed for you, so the compiler refuses to let you read a local before you've assigned it.

```java title="Locals.java"
public class Locals {
    static int field;
    public static void main(String[] args) {
        int local;
        System.out.println(field); // fine, prints 0
        System.out.println(local); // [!code error]
    }
}
```

`error: variable local might not have been initialized`
</Gotcha>

## why two kinds of memory

because they die differently.

a frame dies the instant its method returns. the JVM doesn't clean up anything, it just moves a pointer back down, so allocating and freeing locals is basically free. but that only works because nothing outlives the call.

objects need to outlive the method that made them (you return them, store them in lists, hand them to other threads). so they go somewhere that doesn't care about calls: the heap. the price is that someone has to figure out when an object is actually dead. that someone is the [garbage collector](/learn/gc/gc-fundamentals).

## when the stack runs out

a stack is a fixed-size block (set with `-Xss`). every call pushes a frame, so recursion without a base case eventually runs out of room.

```java title="Main.java"
public class Main {
    static int calls = 0;
    static void down() { calls++; down(); }

    public static void main(String[] args) {
        try {
            down();
        } catch (StackOverflowError e) {
            System.out.println("overflowed after " + calls + " calls");
        }
    }
}
```

<StackOverflowMeter />
</Figure>

<Deep title="why the same program overflows at different depths">
run that program twice in a row inside the same JVM and the second run goes deeper. on jdk 25 with `-Xss1m` it was 20,773 calls cold and 57,948 once the JIT had compiled `down()`.

interpreted frames are generous: they carry the full local array, an operand stack and bookkeeping for the interpreter. compiled frames only keep what the optimized code needs. same method, smaller frames, more of them fit. so "how deep can i recurse" has no single answer, which is a good reason to never design code that depends on it.
</Deep>

the heap can run out too. that's `OutOfMemoryError: Java heap space`, and it's a whole different story (spoiler: usually a leak). see the [OOM zoo](/learn/deep-dives/out-of-memory-zoo).

<Deep title="objects that never touch the heap">
"every object lives on the heap" is the language's promise. the JIT is allowed to cheat as long as you can't tell.

if escape analysis proves an object never leaves the method that created it (never returned, never stored in a field, never passed somewhere that keeps it), C2 can skip the allocation entirely and keep the fields in registers. it's called scalar replacement. your code still looks like it allocated a `Point`, you just never paid for it. more in [JIT optimizations](/learn/jvm/jit-optimizations).
</Deep>

<Interview q="where are static variables stored?">
in HotSpot (the JVM you're almost certainly running), static fields live inside the class's `java.lang.Class` object, on the heap. the class metadata itself (method bytecode, the constant pool) lives in metaspace, which is native memory. before java 8, metadata lived in permgen, a fixed-size slice of the heap that loved to run out. bonus point: a `static final` primitive set to a compile-time constant gets inlined by javac into every place that reads it, so at runtime nobody reads the field at all.
</Interview>

<Keylines>
- every call gets a frame. the frame dies when the call returns.
- objects live on the heap. variables hold arrows to them.
- `=` always copies what's in the slot. for objects, that's the arrow.
- two arrows to one object means changes through one show up through the other.
- an object with no arrows left is garbage. the GC decides when to clean it up.
</Keylines>
